# Deferred scope (v2 and later)

Items deliberately left out of the current milestone. Solve the smallest version first; real use
decides which of these come back. Add the source (kickoff, spec NN, task Tn) and the reason.

| Item | Reason deferred | Source | Revisit when |
|---|---|---|---|
| Semantic search (local model or embeddings API) | Text search is fast and free at current volume | kickoff | Text search misses notes the owner knows exist, repeatedly |
| Other LLM providers | One provider first; the LLM interface keeps the door open | kickoff | A user asks for one, or Anthropic pricing changes the budget |
| Install without n8n | n8n holds credentials and approvals; replacing it is a large project | kickoff | Installs fail because users lack n8n |
| Several owners in one install | One owner per install keeps auth and config simple | kickoff | A team asks to share one server |
| Published container images (registry) | The server builds the image from the repository | kickoff | Builds on small hosts become too slow |
| Deploy from CI | Deploy is infra and tier C; manual deploy is one command | kickoff | Releases become frequent enough that manual deploy hurts |
| Meeting analysis in the pipeline | Runs in the owner's subscription through the analizar-reunion skill (docs/adr/0004-meetings-without-llm.md) | kickoff | The owner wants analyses without asking and accepts the API cost |
| OAuth scopes (read versus write) | One owner per install; all-or-nothing access is enough for now | spec 02 | A client the owner wants read-only access for |
| Client ID Metadata Documents and OpenID discovery | Dynamic registration covers the target clients today | spec 02 | A target client supports only CIMD or OIDC discovery |
| Second factor and remembered consent at sign-in | Passphrase plus lockout is the minimum; sign-in happens once per client | spec 02 | The endpoint sees real brute-force attempts, or the owner asks |
| Archive through MCP | Archiving is rare and stays in Obsidian or later features | spec 02 | The owner asks an AI client to archive notes often |
| Other coding clients and claude.ai chats | The plugin captures Claude Code sessions only; other clients have no session-end hook | spec 03 | The owner works often in another client and wants those sessions saved |
| Automatic meeting analysis | Analysis stays in the owner's interactive session through the analizar-reunion skill | spec 03 | The owner wants analyses without asking and accepts the cost |
| Per-project area routing | One area setting, or TWOBRAIN_AREA per session, is enough for now | spec 03 | The owner keeps projects in several areas and sets the area by hand too often |
| Installing Docker, n8n, DNS or TLS certificates | Each has its own official installer; the guide links them | spec 04 | Most installs fail before the setup step |
| Windows or macOS hosts for the service | The reference and target hosts are Linux Docker servers | spec 04 | An owner wants to run the service on a desktop machine |
| Bundled reverse proxy | n8n installs already run one; snippets for Caddy and nginx cover it | spec 04 | Installs fail at the proxy step |
| HTTPS git remotes with a token | A per-repository SSH deploy key is narrower and never lands in .env | spec 04 | The owner's git host has no deploy keys |
| Rename and delete transcripts in Fireflies (delete after N days) | Irreversible change to the owner's data in a third party; the API is plan-dependent and `deleteTranscript` is rate limited; the vault copy is enough for now | spec 05 | Fireflies storage limits force manual cleanup |
| Create person notes from meeting attendees | Attendee lists hold many one-off contacts; person notes come from the plugin and the owner | spec 05 | The owner adds person notes for meeting attendees by hand often |
| Rename a stored meeting when its calendar event changes | Stored file names are stable targets of the owner's links | spec 05 | Renamed events leave stale meeting names often |
| Backfill of historical transcripts | The route accepts old transcripts, but a bulk import flow and its API quota need their own plan | spec 05 | The owner wants past meetings in the vault |
| Other meeting sources (Zoom, Teams, Otter) | Fireflies and Gemini cover the reference install | spec 05 | An owner records meetings with another tool |
| Fireflies webhook signature check in n8n | The webhook carries only an id resolved with the owner's key behind a random path | spec 05 | Forged webhook calls appear in n8n executions |
| Paid Fireflies plan features (webhooks on a higher plan, higher API limits) | The owner's current plan costs USD 0 and the poll stays within its daily limit | spec 05 | The owner's usual meeting volume no longer fits the daily budget |
| Email attachments in capture | Bodies carry the decisions; attachments need storage, size and scrub rules of their own | spec 06 | The owner often needs a file that only came as an attachment |
| Telegram alerts for git conflicts | Conflicts are rare and logged; an alert path needs its own bot routing | spec 06 | Conflicts happen often enough to be missed in the logs |
| Moving or reclassifying existing notes | Capture only creates notes; reorganizing belongs to routines | spec 06 | Captured notes keep landing in the wrong place |
| Other chat sources (WhatsApp, Slack) | Telegram covers the reference install and has a free bot API | spec 06 | The owner captures ideas mostly in another app |
| Multi-user bots | One owner per install | spec 06 | Several people share one vault |
| Updating a stored email note when its thread gets new messages | One note per thread at first capture keeps the flow idempotent | spec 06 | Long threads keep changing after capture |
